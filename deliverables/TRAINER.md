# Trainer builds — ROM-free report

Target: [minimal64](https://github.com/DeMEdPit/minimal64) — a C64 emulator
that ships **no Commodore ROMs** (custom 252-byte kernal at $E000; BASIC and
character ROM banked in but all zeros). Verified here by compiling minimal64
natively (`tools/m64-harness/`) and running every build **on minimal64
itself**, headless, with scripted input and framebuffer screenshots.

## Corrections to the original brief

- There was never a Claude-built trainer: the menu is the game's own boot
  "OFFICIAL TRAINER" screen by the original author (`cheatmenu.asm`). It has
  **five** cheat toggles, not four (infinite lives, boulder / spike / nasty
  resistance, pass-thru-doors).
- The menu makes **zero KERNAL calls** — it already scans the CIA keyboard
  matrix and writes screen memory directly. Its actual ROM dependency is the
  **character ROM**: it points the VIC at the char-ROM shadow ($1800 in bank
  0) for its glyphs. On minimal64 that ROM is zeros, so the stock menu runs
  *invisibly* (`screenshots/` — the stock build shows a black menu screen,
  yet fire skips it and the game plays perfectly: `stock-m64-title.png`).

## The three files (`deliverables/prg/`, sorted by target: the two new builds sit in `minimal64/`, the kernal one in `c64-roms-required/`)

| File | bytes | what it is |
|---|---|---|
| `tony-trainer-kernal.prg` | **56,480** | the current stock build, untouched (menu readable only with a real character ROM) |
| `tony-trainer-romfree.prg` | **56,520** | same five-toggle menu, rendered with the game's own embedded font — fully readable bare-metal |
| `tony-trained-nomenu.prg` | **55,770** | no menu at all; boots straight into the game with **infinite lives ON**, all other cheats OFF, baked at assembly time |

All ≤ 70,000 bytes; all load at $0801 with the stock `SYS 2240` stub, which
minimal64's injector parses natively. MIT headers and credits untouched.

## Build 2: `tony-trainer-romfree.prg`

Generated by `tools/make_trainers.py`; new module
`src/kickass/cheatmenu-romfree.asm` replaces `cheatmenu.asm` (same menu
content, same key/joystick logic verbatim). The display path changes:

- runs at the original boot position (before unpack, loaded image intact),
- copies the game's embedded 37-glyph font (@, A-Z, 0-9) from its load-time
  location to **$E800 — free RAM above the end of the loaded image** — and
  shows a screen at $EC00 through the $C000 VIC bank (a build-time assert
  guarantees the scratch area stays clear of the image),
- wording recast into the font's glyph set (caps + digits only).

Verified on minimal64: menu renders (`trainer-m64-menu.png`), pressing Y on
"INFINITE LIVES" records YES and advances the highlight
(`trainer-m64-menu-yes.png`), RETURN starts the game, and the cheat byte
(zero page $2D) reads **$04** in-game (`peek` via the harness). Also verified
in VICE with real ROMs — note the stock quirk, present in the original too:
an autostart-typed RUN's trailing RETURN is still held in the matrix when the
menu first scans, so autostart runs skip the menu instantly; with a manual
LOAD/RUN or on minimal64 it waits normally.

## Build 3: `tony-trained-nomenu.prg`

Generated by `tools/make_trainers.py`: the boot's `jsr cheatMenu` becomes a
two-instruction init of `gameCheatState` from the assembly-time constant
`TRAINED_CHEATS` (default `CHEAT_INFINITE_LIVES`; edit one line and rerun the
generator for other variants — the author left `CHEAT_INITIAL` as exactly
this kind of hook). The menu module is dropped from the binary entirely
(−710 bytes vs stock). Verified on minimal64: boots straight to the title
(`trained-m64-title.png`), and $2D reads $04 both at the title and during
gameplay — the flag persists into play.

## ROM-reference verification (both new builds)

**Runtime proof (strongest):** every build boots, menus, and plays on
minimal64, whose BASIC/char ROMs contain zeros and whose kernal is 252 bytes
of its own code. Nothing that depended on Commodore ROM content could run.

**Static proof:** `tools/check_romfree.py` linear-sweeps the 6502 code
regions (game code $08C0–$449E from the KickAssembler symbol file, plus the
menu block $B4D9–$B791 which executes pre-unpack) for JSR/JMP into
$A000–$BFFF / $E000–$FFFF, indirect jumps, and hardware-vector writes.
Every hit vetted against the symbol map:

| finding | verdict |
|---|---|
| `JSR $A000` / `JSR $A003` | the SID player at MUSIC_MEM — **RAM** under the banked-out BASIC ROM (game runs RAM_IO_RAM); the music is our own data copied there |
| `JSR $B4D9` (romfree) | the menu module itself — our RAM-resident code in the load image |
| writes to $FFFA–$FFFF | copper64 installing **RAM** interrupt vectors with the KERNAL banked out — the correct bare-metal technique |
| `JSR $FFFF` ×2 | self-modifying call placeholders (`animateAddr:`) patched to code addresses before first use |
| `JMP ($013F)/(0141)` | c64lib invoke-framework RAM vectors |
| `JMP ($6E6D)` at $448E | false positive — bytes inside the dashboard *map data* ($43FE–$449E) |

Zero actual references into ROM address space as ROM.

## What surprised us (changelog notes)

1. **First attempt crashed with PC in zero page.** Calling the menu *after*
   unpack — while it still lived in the Movable segment at $B4D9 — meant
   `unpack` had already overwritten the menu's own bytes with the music data
   it copies to $A000–$BFFF. Executing music as code ends badly. Hence the
   final design: original call position, font copied out instead.
2. The Code segment has only **171 bytes** of headroom before MUSIC_MEM —
   nothing meaningful can be added there; new boot-time code must live in
   scratch RAM above the image (as the menu's font/screen now do).
3. minimal64's PRG injector parses the BASIC `SYS` line itself and hands the
   address to its custom kernal via a zero-page mailbox ($14/$15/$16) —
   which is why the stock boot stub needs no changes at all.
